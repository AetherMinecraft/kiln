Kiln feature plan

Relay-owned schedules

Add reusable, ordered scheduled actions that continue to run when Hearth is offline. Hearth remains the place where users create and inspect schedules; each Relay owns its clock, execution, and durable local history.

Branch: feat/schedules Cron + friendly presets Multiple targets Offline capable Ordered actions
Core outcome A user can create one daily schedule that announces a backup, backs up every selected server or database, and announces completion—even while Hearth is unavailable.
1. Define Hearth stores the editable schedule and permissions.
2. Deploy A revisioned projection is sent to every target Relay.
3. Execute Each Relay calculates time and runs its local targets.
4. Reconcile Results and history sync back to Hearth when available.

User experience

Navigation and list

Add Schedules directly above Backups in the sidebar. The list shows the name, target count, last result, deployment health, and the Relay-confirmed next run.

Schedule editor

A guided form covers name, timezone, timing, targets, and ordered actions. Friendly choices such as “Daily” produce canonical cron; an advanced field accepts a five-part cron expression.

Compatibility preview

Before saving, clearly show which action and target combinations will run or be skipped. Skips are expected behavior, not failures.

Schedule detail

Show deployment revision, acknowledgement per Relay, next occurrences, and run history that can be expanded down to target and action attempts.

Example schedule

name: Backup My Server Daily timing: Daily at 12:00 AM timezone: America/New_York targets: - Server A - Server B - Database A actions, in order: 1. console_command: say Server backing up... 2. backup: <destination> 3. console_command: say Server backup completed!

Servers run all three actions. The database skips both console commands, runs its backup, and finishes with a successful/no-op result rather than a failure.

Architecture and ownership

Hearth owns

  • Draft schedule definitions and validation
  • User permissions and deployment intent
  • Cross-Relay summaries and the history mirror
  • The schedule editor and operational views

Relay owns

  • Cron calculation and authoritative next-run time
  • Durable claiming and execution
  • Local capability and policy decisions
  • Authoritative attempt history while disconnected
One projection per Relay A schedule spanning three Relays is deployed as three independently executable projections. There is no cross-Relay barrier, so a slow or offline Relay never blocks work on another Relay.

Schedule changes use monotonically increasing revisions. A Relay acknowledges the revision it has durably stored. Disable and delete operations deploy tombstones. On reconnect, Hearth and Relay compare revisions and reconcile, including the case where a Relay committed a change but its acknowledgement was lost.

Permissions and security

Schedule permissions

Scheduling has separate read, create, update, and delete permissions, checked independently for every selected target.

Underlying action permissions

Creating or updating also requires the normal permission for each compatible action: console write, backup create, or target power. The editor only offers actions allowed on the selected targets.

Existing schedules are immutable without full access

An update first authorizes every action in the stored schedule, then authorizes the proposed definition. A user cannot gain edit access by removing an action they are not allowed to perform.

Deletion is a safety control

Delete requires schedule-delete permission on every target, but not each action permission. This lets an authorized operator stop unsafe automation without granting the ability to run its actions.

Server authority is final UI controls improve clarity, but Hearth repeats every permission and target check before persisting or deploying a schedule.

Modular actions and target compatibility

Implement a small code-level action registry. Each action provides its input schema, supported target types, permission check, display summary, and Relay executor. Executors reuse the existing server, lifecycle, database, and backup services rather than creating a second execution system.

Action Server Database Relay
Console command Run Skip unsupported Skip unsupported
Trigger backup Run Run Run platform backup
Power action Run Run Skip unsupported

Unsupported combinations are recorded as skipped_unsupported. They do not fail the target and do not stop later compatible actions.

Execution rules

Ordering

Actions run serially for each target. Targets run independently, so a backup on Server A does not hold up Server B.

Failure

An executor failure stops later actions for that target only. Unsupported skips continue to the next action.

Overlap

If the same target is still running when its next occurrence is due, only that target records skipped_overlap.

Downtime and crashes

There is no catch-up replay. Missed ticks are summarized. A crash marks active work interrupted and does not replay it automatically.

Time behavior

  • Store a five-field cron expression with an IANA timezone.
  • Friendly presets such as Daily normalize to canonical cron before deployment.
  • During a spring-forward gap, a nonexistent time is skipped. During a fall-back fold, the occurrence runs once at the first mapped instant.
  • A deterministic occurrence key prevents duplicate execution after clock rollback or process restart.
  • Drafts show a preview; deployed schedules show the next time confirmed by the Relay.

Status model

Level Statuses
Action attempt succeeded, failed, skipped_unsupported, skipped_missing, skipped_policy, interrupted, not_run
Target run succeeded, noop, failed, interrupted, skipped_overlap
Relay occurrence succeeded, partial, failed, noop, interrupted, missed
Hearth aggregate Adds pending and unknown when a Relay has not reported yet; unreachable does not mean failed.

Scheduled backup design

Scheduled backups stay in the existing serial backup manager. The schedule target waits for the backup to reach a terminal result before continuing to its next action, which preserves the current queuing, locking, and progress behavior.

Exactly-once identity

Relay derives stable IDs from the schedule occurrence, target, and action. Hearth uses those same IDs for idempotent quota reservation and catalog import, so response loss does not create a second backup or consume quota twice.

Offline operation

Local backups continue without Hearth. Restic S3 can use a previously deployed repository configuration. Finite plans use a Relay-held resource budget; exhausted budget skips before creating an artifact.

Full S3 while indefinitely offline is an explicit opt-in It requires persisting least-privilege credentials on the Relay with strict file permissions, redaction, audit, and rotation. Without that opt-in, the attempt is visibly skipped as Hearth-dependent rather than failing mysteriously.

Data, identity, and history

Hearth records

Schedule, ordered action, target, deployment revision, occurrence, target run, action attempt, and offline backup budget records.

Relay records

Deployed schedule projection, occurrence, target run, attempt, capability snapshot, policy result, and history synchronization cursor.

Deterministic identity chain

  1. Occurrence ID derives from schedule, scheduled UTC instant, and Relay.
  2. Target-run ID derives from occurrence and target.
  3. Attempt ID derives from target run and the action’s stable ID—not its array position.
  4. Backup/task IDs derive from the attempt ID.

History synchronization uses stable IDs plus a cursor, making repeated pages safe. Relay prunes only acknowledged history, with retention and a hard cap; any truncation is surfaced rather than silently hidden.

Acceptance gates

  • A schedule runs exactly once while Hearth is stopped.
  • Relay downtime across multiple ticks creates a missed summary and does not replay old work.
  • A crash during an action records interruption without duplicating the action after restart.
  • A slow backup causes overlap skipping only for that target; other targets still run.
  • A deleted target is skipped while valid targets and later schedules continue.
  • Unsupported actions skip cleanly and later compatible actions run.
  • A lost Hearth reservation response consumes quota once and imports one backup.
  • An exhausted offline budget creates no backup artifact.
  • A committed tombstone with a lost acknowledgement reconciles on reconnect.
  • DST spring gaps execute zero times and fall folds execute once.
  • Repeated history pages do not create duplicate records.
  • An unreachable Relay appears pending or unknown globally, never as a fabricated failure.

Key decisions and boundaries

What is deliberately included in version one?
Code-level modular actions, ordered execution, multi-target and multi-Relay deployment, cron with presets and timezones, durable Relay execution, history, next-run visibility, compatibility skips, console commands, backups, and power actions.
What is deliberately excluded?
No cross-Relay transaction or barrier, no automatic catch-up replay, no automatic action retry policy, and no runtime-loaded plugin system. New action types are added through the typed registry.
What was retained from external review?
Keep backups in their existing serial queue; make target ordering and statuses explicit; reconcile revisions after lost acknowledgements; use deterministic identities for backup idempotency; and treat an unreachable Relay as unknown rather than failed.
How is Pterodactyl used as inspiration?
Retain the useful idea of ordered schedule actions and clear failure behavior, while moving execution ownership to the Relay so schedules remain available without the panel.
